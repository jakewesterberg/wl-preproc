# Reading a lost eye from what OpenIrisDPI writes

**A defect found while answering wl-xcon's ask 9** (`HANDOVER-wl-expcontroller.md`, its XC-095).
`EyeQuality`'s tracking loss and blink rate, and the validity mask's `blink`, all read
`DataQuality` below 100, which OpenIrisDPI writes as 100 on every frame: both figures read zero on
a real recording, the mask never labelled a blink, and the detectors were offered frames the
tracker had lost.
- **Branch:** `fix/eye-loss`, forked from `main` at `3885724`.
- **Spec:** `docs/superpowers/specs/2026-10-11-eye-loss-design.md`, approved 2026-10-11, with
  amendments 1–7 made while proving the plan.
- **Plan:** `docs/superpowers/plans/2026-10-11-eye-loss.md`.
- **The requester's choices:** fix it next; one rule, used by both the validity mask and
  `EyeQuality`.

Every line of the plan was proven in a scratch branch, and replayed from the plan's own text,
before the plan was written.

---

## 1. What was built

- **One rule, `ohdpi.TrackerLoss`** (`read_tracker_loss`), per eye per frame: a blink where the
  pupil was not found (width or height 0); a lost feature where P1 or P4 has a coordinate at 0 or
  `DataQuality` is below 100 (the requester's decision after the review, spec amendment 8);
  unreadable where any of the seven columns is not a number.
- **The validity mask reads it:** a blink is `blink`, a lost feature `invalid` (the new criterion
  `feature_lost`), an unreadable frame `invalid` through `non_finite`.
- **`EyeValidity.frac_feature_lost`,** and a refusal in `populate()` while the process reads the
  table without it, naming the statement and a restart.
- **`EyeQuality` counts by the same rule:** tracking loss is every frame lost or unreadable, and a
  blink a run of frames whose pupil was not found, runs under 100 ms apart counted as one. On the
  reference recording: 3.81% and 0.108 Hz for the left eye, 3.52% and 0.091 Hz for the right,
  where both read zero.
- **`gaze.tracking_loss_fraction`** counts by the rule too.

## 2. What the other repositories must do

- **A development database** adds the column; until it does, and the daemon is restarted, the
  mask's stage masks nothing and names the statement (spec §3, amendment 1). No real database
  exists yet. With `<prefix>` the database prefix:

  ```sql
  ALTER TABLE `<prefix>detect`.`__eye_validity`
    ADD COLUMN frac_feature_lost double DEFAULT NULL COMMENT '' AFTER frac_blink;
  ```
- **wl.works:** nothing. The report's format and the NWB file are unchanged.
- **wl-xcon:** nothing to do. Its ask 9 is answered as fixed, and its XC-006 learns that
  OpenIrisDPI writes a feature it did not find as 0.

## 3. Still open

- **A real recording's figures move** (spec amendment 6): masks, detections, the seven-way
  scores and the main sequence computed from it before this change keep the old figures until
  deleted and recomputed. No real recording has been processed by any database yet.
- **A stored mask does not say which rule made it,** but a `computed` row whose
  `frac_feature_lost` is NULL was made before this rule, and only such a row.
- **Partial blinks:** the pupil's height falls in the 10 ms before a lost run and recovers over
  about 40 ms after it. The mask's dilation covers 10 ms either side; the rest of the recovery is
  offered to the detectors.
- **The behaviour cameras could help,** the requester noted (spec amendment 7): a view of the
  eyelid independent of the tracker, once that system is built (wl-xcon's P9).

## 6. The final review

A fresh Opus reviewer read the whole branch (`3885724..455b61d`), ran the branch's tests on both
interpreters, and reproduced every figure in spec §1, §4 and amendment 6 from the reference
recording through the branch's own functions. It found **no Critical, one Important and eight
Minor**, set seven behaviours aside, and judged the branch ready to merge with fixes. It also found
a benefit nobody had named: 61% of the left eye's glitch-repaired samples (6,684 of 10,969) and
45% of the right's are frames the rule now calls lost, so the detectors were being offered gaze
interpolated across P1 dropouts, which the mask now withholds.

**Fixed, in one pass** (`4f28441`):
- **The Important:** the gated tests' docstrings quoted figures this change moved, with no note
  (spec §5). Nyström–Holmqvist's unmatched-saccade table and both-eyes figures are restated to
  this run's output, the 2026-09-28 figures kept as notes; Otero-Millán's refutation carries a
  dated note with the current figures; `test_detect_populate.py`'s non-vacuity count carries the
  current one.
- **Three Minors, re-graded Important by their effect:**
  - `_lacks_feature_lost()`'s positive case ran in no test, so a `return False` slipped through:
    `test_a_table_read_without_the_column_is_refused` now reads a heading without the column.
  - The "parks no key" check could not fail, nothing being pending: the test lands a fresh
    session first, and fails on its parking assertion with the refusal moved into `make()`.
  - The handover told wl-xcon P4 "almost never" goes to 0, true inside blinks only; outside them
    P4 is at 0 on 1.13% of the left eye's frames, the eye looking up, which is XC-006's question
    (spec amendment 9).
- **The requester's decision on Minor 4** (spec amendment 8): `DataQuality` below 100 is a lost
  reflection, withheld as `invalid`, not a blink, since it says nothing about the pupil. The two
  fixtures that faked a blink through `DataQuality` write one as OpenIrisDPI does, and the
  consensus test now asserts its planted frames are stored as `blink`.

**After the fixes,** the full suite on both interpreters: 3.11 **2339 passed, 27 skipped, 1 deselected, 1 xfailed**; 3.13 **2339 passed, 28 skipped, 1 xfailed**.
CI, without the references, should show about 2330 (`main`'s 2308 and these 22).

**Deferred, Minor:**
- the drop-and-restore test NULLs `frac_feature_lost` on rows earlier modules inserted (harmless
  in file order; its docstring says the rest of the suite is unaffected);
- `EyeValidity.frac_glitch_repaired`'s comment says repaired samples stay usable, and over half
  the left eye's are now masked as lost;
- criterion counts still "six" in `schema/detect.py` and `cli/report.py`, "all five" in
  `tests/cli/test_detect_report.py::_validity_row`;
- wording: `EyeQuality`'s column comment omits unreadable frames; `TrackerLoss` calls an
  unreadable frame "in neither", true only if no other column is 0; this handoff says "not a
  number" where the code tests "not finite", and §3 leaves `EyeQuality` rows out of what stays
  stale until recomputed;
- a follow-up: the gated tests' scale heuristic (the pooled 99th percentile) is set by lost
  frames, 218.6 px against 163.1 px without them.

**Set aside by the reviewer, and the rulings on them** (all stand): an unparseable token in a
loss column fails the session, as every column `read_columns` reads does; rows computed before
this rule keep their figures until recomputed; the extra column reads; what "under 100 ms apart"
means at the edge, immaterial on real data; detectors filtering across masked samples; partial
blinks beyond the dilation (§3); and whether glitch repair should skip lost frames, the glitch
spec's question.
